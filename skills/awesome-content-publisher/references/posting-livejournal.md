# livejournal

Check: `livejournal.com/post/` (the old `update.bml` redirects there) renders the editor with the journal name in the header; signed out shows the login page. The journal is `<journal>.livejournal.com`.

Compose: `textbox "Title"` with a live `0/100` counter, a hard 100-character cap. The body is a block editor (contenteditable, placeholder `Start typing, add images or just press "/"`); `/` opens the block menu and `Choose File` beside it takes an image. Tags go in the tags textbox (`Start writing tags, separated by commas`), from the post file's `hashtags`. `Visible to all` is the security control and stays on its default. `Tune in and publish` opens the publish settings and posts. Drafts live at `/post/list/`; an interrupted run leaves one there.

Read-back: `<journal>.livejournal.com/<id>.html`, newest entry from the journal's front page.

The editor is Draft.js and it has no code style, so an HTML paste loses every `<pre>` and every heading level silently. Two runs shipped a post whose commands were run-on prose and whose section headings were ordinary paragraphs, and both looked acceptable in the composer. The body therefore goes in as text and is then styled through the editor's own controls, the way `patreon` and `quora` are handled.

**Commands go in a spoiler, one per fenced block.** The spoiler is the last control on the selection toolbar and it is what this editor has instead of a code style: it publishes as `span.lj-spoiler`, a click-to-open row labelled with the caption in square brackets, which suits a command block better than the indented quote does. Build the whole block first as one Draft block with `Shift+Enter` between lines (a soft break keeps the next line in the same block, a plain `Enter` starts a new one), then select all of it and apply the spoiler once. Give each block a caption that names what is hidden - `commands`, `config`, `DeepSeek rates` - because the caption is the only thing the reader sees before opening it.

**Headings are applied by selection.** Select the heading's text and pick `H2` or `H3` from the toolbar that appears over the selection, matching the source's level; `B` is for a bold lead where the source has one, not as a substitute for a heading. Count the applied headings against the source's `##` and `###` counts before publishing.

Alignment inside a command block survives only as non-breaking spaces, the same as on the other editors with no `pre` node: convert every run of two or more spaces before the text goes in.

The tags field has `maxlength="40"` and truncates in silence. Four tags of ordinary length exceed it as one comma-separated string — one run shipped `vibecodi` where `VibeCoding` was meant — so enter tags one at a time, each followed by a comma, which commits the tag and clears the field. LiveJournal lowercases what it stores, so a chip that already exists in lowercase is the same tag. Read the committed chips back before publishing.

Two more things the field hunt gets wrong: the tags input carries no `placeholder` attribute (the prompt is a sibling element), so a placeholder-based query finds nothing — match it by its `editableInput` class instead. And the publish panel's own `Publish` button only exists while that panel is open; the panel closes when anything else is clicked, and the tags field clears with it, so fill tags and publish in the same pass.

Driven end to end on a reformat, with the selectors measured:

**The selection toolbar only exists after a real mouse selection.** A programmatic `Range` puts text in `getSelection()` and raises no toolbar at all, which reads exactly like a platform with no formatting controls. The sequence that works per block: `scrollIntoView`, a `page.mouse.click` a few pixels inside the block, `Home`, `Shift+End`. Then `div.js--inline-toolbar` mounts, as five `ul.group` holding eleven `li`: bold, italic, strikethrough | `js--heading2-btn`, `js--heading3-btn` | bulleted, numbered | quote, highlight | `js--link-btn`, spoiler.

Each `li` carries its own name as visually hidden text, so read the labels rather than counting icons: `bold`, `itallic` (sic), `strikethrough`, `heading 2`, `heading 3`, `non-numbered list`, `numbered list`, `quote`, `highlight`, `link`, `spoiler`. Index 7 is the real blockquote and index 8 is `highlight`, the indented block that earlier passes reached for as a quote - it produces `aentry-post__block--highlight` and toggles off on a second click. Re-read the toolbar's rect immediately before clicking it: it is a portal positioned near the selection, so a rect captured before the selection moved lands somewhere else entirely - one pass clicked at the block's own x and missed by 160px.

**The spoiler is the eleventh `li` (index 10) and it takes a caption.** Clicking it replaces the toolbar with a caption field, `input[placeholder="Spoiler text"]`; type the caption and press `Enter` to commit. The field **keeps the caption from the previous block**, and typing into it then interleaves the new text with the old - one pass produced `the othe other pathsthepathsr paths` and committed nothing. Click the field, `Control+a`, `Delete`, then type.

**The spoiler wraps exactly the selection, so the selection has to be the whole block.** Verify it before clicking: `window.getSelection().toString().length` must equal the block's `innerText.length`. `Home` + `Shift+End` takes one *visual* line, and `Shift+ArrowDown` counts visual lines too, so the same block needs a different number of presses depending on whether it currently carries a block style - one press too many runs past the block into the next heading. Press `Shift+ArrowDown` while the count is below the target, then `Shift+ArrowRight` until it matches exactly. A selection that falls short publishes a spoiler with the block's tail hanging outside it, which is the one failure that looks fine in the composer.

**The editor does not always draw the eye for a spoiler it has applied.** `svgicon--spoiler` reads 0 inside the block while the entity is there and publishes normally; it stayed invisible through a reload and through two `Update`s. So never read the result from the editor: read it from the autosaved draft. The editor URL carries it - `?draft=https://<journal>.livejournal.com/dN.html` - and opening that address in a second tab renders the post exactly as it will publish, `span.lj-spoiler` and all. The `(saved at HH:MM:SS)` line beside `Delete post` says when the draft last changed; a click that changed nothing leaves the timestamp alone, which is itself a useful signal.

**Fix a wrong spoiler by re-applying, not by editing text.** Selecting a wider range and applying the spoiler again replaces the existing one, caption included. Deleting the block's text and retyping it does *not* clear the entity - the retyped characters inherit it - and a synthetic `paste` of the same text is swallowed with no change at all. Where the eye *is* drawn, clicking it reopens the caption popover, which carries a trash button (`svgicon--delete`) that removes the spoiler cleanly.

**`js--heading2-btn` toggles.** Clicked on a block that is already a heading it *removes* the heading, which is how one pass turned all seven section headings into plain paragraphs in a single loop. Read each block's tag first and only click where the block is not already the level you want. In the editor's own DOM the heading levels render as `h1` (Heading 2) and `h3` (Heading 3), so a check written against `h2` finds nothing on a post full of headings.

**`Shift+ArrowDown` does not extend a selection across blocks whose text wraps**, so a multi-block selection built that way silently covers one block and the style lands on one line of a four-line group. Apply the style per block, or build the multi-line block first and style it once.

**Joining existing paragraphs into one block:** put the caret at the true end of the first block with a `Range` collapsed to `selectNodeContents(block).collapse(false)`, press `Delete` to pull the next block up, then `Shift+Enter` to put the line break back. Repeat per line. `End` is not a substitute - these lines wrap, and `End` stops at the end of the visual line.

**A line ending in a slash token is eaten by the quick-insert menu.** `/` opens LiveJournal's block menu, and a line whose last word is `/models` leaves that menu armed: the next `Delete`, `Shift+Enter` or `Escape` cancels the token and takes the word with it. One group lost `/models` and `Aider` three times in a row this way, and the total character count moved by thirteen while every intermediate read looked correct. The fix is a single trailing space after any line ending in a slash token, which commits it; the space is invisible in the rendered post. Check the text of every command block against the source lines after building it, not only its line count.

**Update commits only from the session that opened the entry.** `editjournal.bml?journal=<journal>&itemid=<id>` opens a page titled *Edit entry* which immediately migrates to `?draft=<journal>.livejournal.com/dN.html`, and the button there reads `Tune in and update` -> `Update`, which publishes back over the entry. Navigating to that draft URL directly in a later call gives a page titled *New entry* whose `Update` hit-tests true and does nothing - two clicks, no navigation, no change to the entry. Recover by opening `editjournal.bml` again: it restores the autosaved draft content into a properly bound session, and the formatting done earlier is still there. Check `document.title` reads `Edit entry` before spending a pass on the body.
