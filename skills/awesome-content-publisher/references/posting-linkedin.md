# linkedin

Check: `linkedin.com/feed/` — the member name renders in the rail. Compose: "Start a post" → the share dialog → the editor → "Post". Read-back: own profile → recent activity/posts.

The editor is no longer Quill. It is TipTap/ProseMirror — `.tiptap.ProseMirror[role="textbox"]` — and `.ql-editor` now matches nothing, so a run selecting on it reports the composer as absent on a page where it is plainly open. Because it is ProseMirror, a synthetic `paste` event carrying `text/plain` is the way to get the body in: the whole text arrives in one call, where per-line typing does not. It does not get the blank lines in, and that distinction is the defect this platform ships most often — see the paragraph below. The same event is what Facebook's composer wants. Two more things measured on this composer: the dialog's own trigger and the Media button respond to `page.evaluate(el => el.click())` but time out under `locator.click({force:true})` — Playwright's actionability never settles on this page, so the untrusted click is the rung that works here, opposite to Facebook where the forced click is what lands. And the alt-text panel is fragile: opening it on a composer that already holds an attachment crashed the whole dialog to *Something went wrong*, losing the draft. Attach, set alt text before typing the body if you want it at all, and treat a crash there as a reason to publish without alt and record `degraded` rather than to retry into a second crash.

A blank line between paragraphs has to be typed, and nothing pasted produces one. This editor's schema drops whitespace-only paragraphs on paste and turns every `<br>` into a paragraph split, so `<p>a</p><p><br></p><p>b</p>`, `<p>a</p><p>&nbsp;</p><p>b</p>` and a `text/plain` body separated by `\n\n` all arrive as the same thing: consecutive non-empty `<p>` blocks with no gap between them. In the composer that looks correct — one paragraph per source paragraph — and it publishes as a wall, every break rendered as a single newline. Measured on a live post: 20 paragraphs in the composer, 19 single newlines and zero blank lines on the published page, at a character count that matched the source. So the pre-submit check counts *empty* blocks, not blocks.

The way that works is a real `Enter` at the end of each paragraph that the source follows with a blank line, and it needs the caret set correctly: `el.focus()` puts ProseMirror's own stored selection back at the end of the document, so a `Range` set before the focus call is discarded and every `Enter` lands at the bottom. Focus once, wait, then per insertion set a collapsed `Range` at the end of the target paragraph and press `Enter`. Walk the paragraph indices from the last to the first so the earlier indices stay valid. Fenced blocks and a label sitting directly above its URL take no blank line — the gap goes exactly where the source has one, which is why the insertion list is derived from the source file rather than applied between every pair.

An already-published post is editable and this is the repair route: the post's `Open control menu for post by <name>` button → `Edit post` → the same TipTap editor loaded with the live body → insert the blank paragraphs → `Save`. The feed then serves the previous render until the page is reloaded, so the read-back is a reload, not a re-query. Reactions and comments survive the edit, which makes this strictly better than delete-and-repost on anything the user's network has already seen.

The reliable way in is `linkedin.com/preload/sharebox/` — it opens the share composer directly, with `.ql-editor[contenteditable="true"]` ready. The profile route works too: the Activity section of `linkedin.com/in/<handle>/` carries a "Create a post" link pointing at that same URL. From the feed, the composer often refuses to mount at all: on a page rendering with ~190 console errors the button was present on one probe and gone on the next, and `?shareActive=true` produced zero editors. Note the feed's own trigger is a `DIV` reading "Start a post", not a `button` — a `button`-only sweep reports it missing and the feed route then looks broken when it was never clicked.

Media: attach BEFORE typing, or the control is gone. The sharebox does carry an image control — `button[aria-label="Add media"]`, class `share-promoted-detour-button`, sitting in the icon row under the editor — but it is rendered only while the composer is empty, and disappears the instant the editor holds text. A run that wrote the body first found no media button, concluded "the sharebox has no media control", and published the post bare. Order: open the sharebox → click `Add media` → `browser_file_upload` → step through the media editor → *then* fill the editor and submit. If the composer already has text, clear it (`Ctrl+A`, `Backspace`) and the button comes back.

The media editor is also where alt text works — unlike X and Instagram, this one is reachable. After the upload the dialog reads `Editor / Edit / Tag / Alternative text / 1 of 1`; click Alternative text, type into its `textarea`, and commit with the Add button (not "Save" or "Done" — those do not exist here). Then Next returns to the composer with the image attached, and the editor mounts again so the body can be typed.

Filling needs `page.keyboard.insertText`. `handle.type`, `keyboard.type` after a coordinate click, and even `el.focus()` reporting success all leave the Quill editor empty; insertText fills it in one shot. Quill reports a few more characters than the source (it renders `\n\n` as `\n\n\n\n`), so compare the URL and the tail rather than the exact count.

Submitting works only through `el.click()` from `page.evaluate`. With the body in place the Post button enables, and a coordinate click, an element-handle click and a force click all leave the activity feed unchanged — the newest post stayed a month old, while a `beforeunload` on the way out confirmed the draft was still sitting there. The untrusted JS click published immediately. Take the last enabled button whose text is exactly "Post"; the draft persists across reloads, so a failed attempt costs nothing and can be finished by hand.

Read-back: `linkedin.com/in/<handle>/recent-activity/all/` should show the post as "Feed post number 1 … now"; the permalink is `linkedin.com/feed/update/urn:li:activity:<id>/`, and the URN is in that page's HTML. LinkedIn rewrites every link to `lnkd.in/<code>` and renders a preview card, so a tail comparison against the source URL fails on a perfectly intact post — check that the `lnkd.in` link and the card title are present instead, and that the original URL still appears in the page HTML.


A post file with `document:` is a document post: the PDF shows as swipeable pages. The share composer's document control takes the PDF and asks for a title, which is the post's `title`; attach it before typing, as with an image. Not driven on a live account yet, so derive the controls from a snapshot. Read-back: the post renders a document viewer with the file's page count.

The editor is **not the same on every account**: one run met `.tiptap.ProseMirror` and another, on a different profile the same week, met `.ql-editor` (Quill) with `.tiptap` matching nothing. That decides the whole fill strategy, because Quill turns a `\n\n` in an `insertText` into a real empty `<p>` while TipTap drops it. Probe for both before choosing, and keep the empty-block count as the gate either way: 13 source paragraphs must leave 12 empty blocks.

LinkedIn rewrites **every** URL in the body to an `lnkd.in` shortlink, including URLs inside command lines. A post carrying `$env:ANTHROPIC_BASE_URL="https://api.deepseek.com/anthropic"` published as `$env:ANTHROPIC_BASE_URL="https://lnkd.in/<hash>"`, so the command a reader copies does not work. The composer offers no code span, so nothing in the composer prevents it — the fix belongs upstream in the post file (`awesome-content-repurpose`, Phase 5), and on a post that already carries a bare command URL the honest options are to drop the command block or to publish and disclose. Editing afterwards does not help: the save re-linkifies identically.

`Edit post` opens a modal whose editor is not reachable the way the composer's is. Across three attempts the modal rendered with the body and a `Save` button visible in a screenshot while `[contenteditable="true"]` matched only the page's comment box, and a coordinate click inside the modal dismissed it. Budget two attempts for an in-place edit here, then hand the exact steps to the user rather than clicking into a live post a third time.

That rewrite is now a writing constraint, recorded in `awesome-content-repurpose`'s Phase 5: a LinkedIn file carries no command whose correctness depends on a URL, and names the setting in prose instead. The publisher's part is to refuse to ship one silently — where a `linkedin` post file still contains a URL inside a command, say so before filling and let the user choose between dropping that block and publishing a command that will not work.
