# AGENTS.md format

How the mined rules become a file every agent reads the same way. The format itself (agents.md, stewarded by the Agentic AI Foundation) fixes almost nothing: standard Markdown, no required fields, nested files allowed, the closest file to the edited path wins, and an explicit user instruction beats all of them. Everything below is the discipline that makes such a file work across agents.

## Section order

Agents skim from the top and some truncate, so order is by how often a line is needed and how costly it is to miss. Leave out any section with nothing project-specific in it.

1. Title and one-paragraph overview — what the project is and the stack in a sentence, so the rest has context. No marketing, no history.
2. Commands — setup, dev, build, test, single test, lint, format, typecheck, codegen. Each in a code span, runnable from the directory the file sits in (say so when a command must run elsewhere). A command that never exits hangs an agent: write the one-shot, non-interactive form (the way CI invokes it, not the watch-mode default), and mark the dev server as long-running.
3. Project map — one line per directory an agent would otherwise have to open to understand.
4. Conventions — the Rule and Migration items from Phase 3, grouped by dimension, each pointing to an exemplar file.
5. Recipes — "Adding a new `<kind>`": ordered steps, each naming a file or a command.
6. Testing — where tests go, how they are named, what is mocked, what integration tests need, what "green" means before a change is done.
7. Boundaries — three tiers:
   - Always — what every change must do (run the gate command, regenerate after a schema change).
   - Ask first — what needs a human decision (new dependency, schema migration, public API change, touching a protected area).
   - Never — what breaks things (edit generated files, commit secrets, rewrite applied migrations), each with its reason in one clause.
8. Git and pull requests — commit subject format, branch naming, what a PR must contain, files that move together.
9. Further reading — relative links to the docs that hold what the file deliberately leaves out (architecture docs, ADRs, CONTRIBUTING). Links, not summaries.

## Line rules

- Imperative mood, one rule per bullet. "Put handlers in `src/routes/`", not "Handlers are generally placed in…".
- Specific over general: a path, a command, a symbol name. A bullet with none of the three is a candidate for deletion.
- Point, don't paste. "Follow `<path/to/exemplar>`" survives refactors; a pasted template drifts from the code within weeks. A snippet is justified only where the pattern is a few lines and has no single exemplar.
- Reasons in one clause, and only for rules that look arbitrary: "never edit `<dir>/` — it is regenerated by `<command>` on every build".
- Relative paths, from the file's own directory.
- No hedging words (usually, generally, try to, where possible). A rule with exceptions names them; a convention too soft to state firmly is a Split and belongs in the report.
- No emphasis inflation. Capitals and "IMPORTANT" on every other line teach an agent that none of it is important. Reserve emphasis for the one or two Never lines that destroy data.
- No counts, dates, generator stamps, or evidence tables — they rot, and they are not instructions.

## Agent-neutral constraints

The file must read as plain instructions to any agent. Before delivery, search the draft for each of these; every hit is removed or rewritten:

- Tool names of any one agent: names of built-in read, edit, search or shell tools; sub-agent, skill, hook or plugin vocabulary.
- Slash commands and dollar-prefixed invocations.
- Import syntax one agent resolves and others print literally — an at-sign before a path, include directives. Use ordinary Markdown links; agents that follow links will, and the rest lose nothing.
- Frontmatter, glob headers, or rule-file metadata from any single agent's rule format.
- Model names, provider names, context-window or token talk.
- XML-style tags or persona lines ("You are an expert…").
- MCP server names — unless the project itself ships the server config, in which case name the config file, not the agent that reads it.
- Shell syntax that works in one shell only. Prefer the project's own runner (a manifest script, a make target, a task file), which is portable by construction. Where a command is OS-specific, say which OS.

Agent-specific instructions that the project genuinely needs belong in that agent's own file, next to the shim, not in `AGENTS.md`.

## Size budget

Every session pays for the file in context before doing any work, and some agents cap what they load (Codex, for one, stops reading project docs past a byte limit, 32 KiB by default at the time of writing, counted across all nested files it merges).

- Root file: aim for under 150 lines; above 250, cut.
- Nested file: under 80 lines, differences only.
- When over budget, cut in this order: project-map lines for self-explanatory directories, conventions a reviewer would call obvious, dimension detail better served by a link. Never cut commands or Never lines to make room.

## Nested files

- One per unit whose commands or conventions differ from the root (Phase 1). Not one per directory.
- Holds only the delta: its own commands, its own conventions, its own boundaries. It does not repeat the root; agents that merge the chain would read it twice, and a fact stated in two files drifts in one of them.
- Opens with one line naming the unit and pointing to the root file by relative link, so an agent that loads only the nearest file knows another one exists.
- Where the root and a nested file disagree, the nested file wins by format rule — state such an override explicitly ("this package uses `<runner>` instead of the root's `<runner>`") so it reads as intended, not as drift.

## Which agent reads what

Support changes release to release. This table is a starting point; check the agent's current documentation before creating a shim, and never create one the user did not pick.

| Agent | Reads `AGENTS.md` | If not, the shim |
| --- | --- | --- |
| OpenAI Codex | Yes, root to working directory, merged | — |
| Cursor | Yes, root and nested | — |
| GitHub Copilot (coding agent, editor chat) | Yes | — |
| opencode, Amp, Windsurf, Jules, Zed, Warp, Devin | Yes | — |
| Claude Code | Reads `CLAUDE.md` | A `CLAUDE.md` beside it holding one line that imports `AGENTS.md` with the agent's import syntax (the import lives in the shim, never in `AGENTS.md`) |
| Gemini CLI | Reads `GEMINI.md` by default | A context file-name setting in the project's `.gemini/settings.json` that lists `AGENTS.md` |
| Aider | Only files it is told to read | A `read` entry for `AGENTS.md` in the project's Aider config |

A pointer file or setting is preferred over a symlink: some platforms and clients turn a symlink into a copy that goes stale without warning, and a symlinked file cannot carry the few agent-specific lines that agent may need.

When a legacy agent file holds project knowledge (Merge mode), move the verified knowledge into `AGENTS.md` and leave the legacy file as the shim plus whatever is truly agent-specific. Two files that both describe the project will disagree within a month.

## Skeleton

Placeholders only; every angle-bracketed slot is filled from evidence or the section is dropped.

```markdown
# <Project name>

<One paragraph: what it is, the stack, the unit layout if a monorepo.>

## Commands

- Install: `<command>`
- Dev: `<command>`
- Build: `<command>`
- Test all: `<command>` · one file: `<command> <path>` · one test: `<command>`
- Lint / format / typecheck: `<command>` / `<command>` / `<command>`
- Before every commit: `<the gate CI runs>`

## Project map

- `<dir>/` — <its one job>

## Conventions

- <Rule, imperative, with a path or symbol.> Exemplar: `<path>`.

## Adding a new <kind>

1. <Step naming a file or a command.>

## Testing
```
